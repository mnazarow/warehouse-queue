# warehouse-queue — полная документация

Система онлайн-записи на склад с кабинетом менеджера, страницей кладовщика,
интеграцией с 1С, SMS-уведомлениями, кэшированием в Redis и поддержкой двух
СУБД (SQLite и PostgreSQL).

Проект существует в **трёх независимых реализациях с одинаковым функционалом и
общим фронтендом**:

| Вариант | Каталог | Технологии | Когда выбирать |
|---------|---------|-----------|----------------|
| **Node.js** | корень (`server.js`) | Node 20, Express, better-sqlite3 | Основной, самый зрелый; проще всего запустить |
| **Go** | `go-service/` | Go 1.21+, стандартная библиотека | Один статический бинарник, минимум зависимостей |
| **Rust** | `rust-service/` | Rust, tiny_http | Максимальная производительность одного бинарника |

Все три отдают один и тот же интерфейс из каталогов `public/` (страница записи,
кабинет) и `private/` (страница кладовщика), используют одинаковую схему БД и
одинаковые HTTP-эндпоинты. Выбирайте любой — поведение совпадает.

## Возможности

- **Онлайн-запись** на временные слоты по складам, с типами «мелкая» (шаг 15 мин)
  и «крупная» (шаг 30 мин) отгрузка; рабочее окно 10:00–17:30.
- **Защита от двойной брони** (атомарное условие `WHERE is_booked=0`), капча,
  ограничение «не раньше чем за 1 час» и «не дальше 2 недель».
- **Кабинет менеджера**: управление слотами (взять/подтвердить/собрать/
  завершить/отменить), справочники, менеджеры, аналитика, настройки.
- **Признак администратора** у менеджеров: вкладки «Настройки» и «Менеджеры»
  доступны только админам. Главный `admin` — всегда администратор.
- **Права доступа по разделам**: для ролей «Менеджер» и «Кладовщик» каждому
  разделу задаётся уровень — нет доступа / только чтение / чтение и запись.
  Проверка выполняется на сервере, а не только в интерфейсе.
- **Страница кладовщика** с доступом по PIN-коду.
- **Интеграция с 1С**: проверка счёта/заказа и оплаты по HTTP, токен API,
  журнал проверок. Организация в заявке берётся из 1С (введённое клиентом
  название заменяется), при счетах разных юрлиц перечисляются все, а в кабинете
  счета сгруппированы по организациям.
- **SMS-уведомления** через sms.ru.
- **Кэширование** свободных слотов в Redis с настраиваемым TTL.
- **Часовой пояс у каждого склада**: время окон показывается по времени склада,
  а клиенту из другого пояса рядом выводится его местное время.
- **Категории товаров у склада**: для каждого склада отмечается, какие группы
  товаров на нём хранятся (справочник общий со вкладкой «Номенклатура»);
  на странице записи клиент раскрывает этот список прямо в плашке склада.
- **Обязательность полей** «Класс машины» и «Вид загрузки» настраивается.
- **Две СУБД**: SQLite (по умолчанию) и PostgreSQL, с миграцией/переключением.
- **Резервные копии**: ручные (скачать/восстановить) и автоматические с
  ротацией.
- **Аналитика**: посещения и брони по интервалам (минуты/часы/дни/недели/годы),
  разбивка по устройствам/ОС/браузерам.
- **Оформление**: светлая/тёмная/киберпанк/фэнтези + 4 сезонные темы, маскот
  (капля воды) с анимацией, баннер cookie, политики ПДн и cookie.
- **Обновление** из git прямо из кабинета (для native-установок).

## Быстрый старт

Самый короткий путь — Node на SQLite, локально:

```bash
git clone https://github.com/mnazarow/warehouse-queue.git
cd warehouse-queue
npm install
npm start
```

Откройте:

- запись — `http://localhost:3000/`
- кабинет — `http://localhost:3000/manager.html` (логин `admin`, пароль `admin123`)
- кладовщик — `http://localhost:3000/storekeeper`

> ⚠️ После первого входа **обязательно смените пароль `admin`** в кабинете
> (вкладка «Менеджеры»).

## Установка — все варианты

Во всех вариантах после установки доступны те же URL и тот же логин
`admin`/`admin123`.

### Node.js — вручную

Требования: Node.js 20+, npm. Опционально PostgreSQL и Redis.

```bash
git clone https://github.com/mnazarow/warehouse-queue.git
cd warehouse-queue
npm install
# по умолчанию SQLite в файле warehouse.db
PORT=3000 npm start
```

PostgreSQL и Redis в Node-варианте **подключаются и включаются из кабинета**
(вкладка «Настройки» → PostgreSQL / Redis) — приложение стартует на SQLite и
переключается на PostgreSQL по кнопке миграции. Предзаполнить параметры можно
через переменные окружения (`PGSQL_*`, `REDIS_*`) — см. раздел
[Переменные окружения](#переменные-окружения).

### Node.js — скрипт на чистый сервер

Ubuntu/Debian, от root. Скрипт ставит Node, готовит каталог, systemd-сервис.

```bash
# SQLite
sudo bash deploy/install-native.sh

# PostgreSQL по умолчанию (ставит и настраивает PostgreSQL)
sudo bash deploy/install-native-pg.sh
```

Подробности — в `INSTALL-NATIVE.md`.

### Docker

Полный стек (приложение + PostgreSQL + Redis + nginx + Let's Encrypt) одним
файлом `docker-compose.yml`:

```bash
cp .env.example .env
# отредактируйте .env: пароли БД, домен, e-mail для сертификата
docker compose up -d
```

Выпуск HTTPS-сертификата:

```bash
DOMAIN=zayavka.example.ru EMAIL=you@example.ru bash deploy/init-letsencrypt.sh
```

Полная инструкция и описание сервисов — в `DOCKER.md`.

### Go — на чистый сервер

Ubuntu/Debian, от root. Скрипт «под ключ»: ставит Go, PostgreSQL (создаёт БД и
роль), Redis, собирает бинарник, поднимает systemd-сервис `warehouse-go`.

```bash
# по умолчанию: PostgreSQL + Redis
sudo bash deploy/install-go-server.sh

# вариант на SQLite
sudo DB_BACKEND=sqlite bash deploy/install-go-server.sh

# свои параметры БД
sudo PG_DB=wh PG_USER=wh PG_PASSWORD='СильныйПароль' bash deploy/install-go-server.sh

# с nginx-прокси под домен
sudo WITH_NGINX=1 DOMAIN=zayavka.example.ru bash deploy/install-go-server.sh
```

Если Go и СУБД уже есть и нужно только собрать/обновить приложение —
`sudo bash deploy/deploy-go.sh`.

Сборка вручную:

```bash
cd go-service
go mod tidy && go build -o warehouse-go ./...
STATIC_DIR=../public PRIVATE_DIR=../private ./warehouse-go
```

### Rust — на чистый сервер

Ubuntu/Debian, от root. Скрипт «под ключ»: ставит Rust (rustup) и сборочные
зависимости (`build-essential`, `pkg-config` — нужны для встроенного SQLite),
PostgreSQL, Redis, собирает release-бинарник, поднимает сервис `warehouse-rs`.

```bash
# по умолчанию: PostgreSQL + Redis
sudo bash deploy/install-rust-server.sh

# вариант на SQLite
sudo DB_BACKEND=sqlite bash deploy/install-rust-server.sh

# с nginx-прокси под домен
sudo WITH_NGINX=1 DOMAIN=zayavka.example.ru bash deploy/install-rust-server.sh
```

Если Rust уже есть — `sudo bash deploy/deploy-rust.sh`.

Сборка вручную:

```bash
cd rust-service
cargo build --release
STATIC_DIR=../public PRIVATE_DIR=../private ./target/release/warehouse-rs
```

> Первая сборка Rust занимает несколько минут (компиляция зависимостей).

### Автодеплой через GitHub

В `.github/workflows/` настроены:

- `deploy.yml` — сборка Docker-образа и публикация в GHCR при push в `main`;
- `go-build.yml` — сборка и `go vet` Go-варианта;
- `rust-build.yml` — `cargo build --release` Rust-варианта.

На сервере автообновление организуется одним из способов:

- **git-pull** по таймеру/вебхуку — `deploy/auto-deploy.sh` (Docker) или
  `deploy/auto-deploy-native.sh` (native);
- **Watchtower** — следит за образом в GHCR и обновляет контейнер (профиль в
  `docker-compose.yml`).

Кнопки «Проверить обновления» и «Обновить» в кабинете (вкладка «Настройки»)
делают `git pull` и перезапуск для native-установок.

## Настройка

### Переменные окружения

**Node.js** (`server.js`):

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `PORT` | `3000` | Порт сервера |
| `TZ_OFFSET_HOURS` | `3` | Часовой пояс склада: смещение от UTC (Москва = 3). Приоритет у настройки в кабинете |
| `BOOKING_MAX_DAYS` | `14` | Горизонт записи в днях. Приоритет у настройки в кабинете |
| `DB_PATH` | `./warehouse.db` | Путь к файлу SQLite |
| `SESSION_SECRET` | из файла `.session-secret` | Секрет подписи сессий. Если не задан, генерируется при первом запуске и сохраняется в `.session-secret` (права 0600) рядом с приложением |
| `ADMIN_PASSWORD` | (случайный) | Пароль главного администратора при создании пустой базы. Если не задан — генерируется и записывается в `ADMIN-PASSWORD.txt` |
| `COOKIE_SECURE` | — | `1`, если сайт работает по HTTPS: cookie сессии не уйдёт по открытому каналу |
| `TRUST_PROXY` | — | `1`/`true`, если за обратным прокси (nginx) |
| `TRUST_PROXY_HOPS` | `1` | Сколько своих прокси стоит перед приложением (для определения адреса клиента) |
| `CORS_ORIGINS` | — | Список сайтов через запятую, которым разрешены кросс-доменные запросы к кабинету |
| `DB_TIMESTAMPS_LOCAL` | — | `1`, если отметки времени в старой базе сохранены в местном времени, а не в UTC |
| `REDIS_OP_TIMEOUT_MS` | `300` | Предел ожидания ответа Redis; после сбоя кэш отключается на 30 с |
| `ALLOW_1C_TOKEN_IN_QUERY` | `1` | `0` — принимать токен 1С только в заголовке `X-API-Token` |
| `BACKUP_DIR` | рядом с БД | Каталог резервных копий |
| `REDIS_ENABLED` | `0` | Предвключить Redis (иначе из кабинета) |
| `REDIS_HOST`/`REDIS_PORT` | `127.0.0.1`/`6379` | Параметры Redis (сид) |
| `PGSQL_HOST/PORT/USER/PASSWORD/DATABASE` | — | Предзаполнение настроек PostgreSQL |
| `SMSRU_API_KEY` | — | Ключ sms.ru (можно задать в кабинете) |
| `SEED_CONNECTORS` | — | Демо-данные коннекторов 1С |

> В Node выбор СУБД делается **в кабинете** (миграция SQLite↔PostgreSQL). Env
> `PGSQL_*` только предзаполняют форму.

**Go** (`go-service`) и **Rust** (`rust-service`):

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `PORT` | `3000` | Порт сервера |
| `TZ_OFFSET_HOURS` | `3` | Часовой пояс склада: смещение от UTC (Москва = 3). Приоритет у настройки в кабинете |
| `BOOKING_MAX_DAYS` | `14` | Горизонт записи в днях. Приоритет у настройки в кабинете |
| `DB_BACKEND` | `sqlite` | `sqlite` или `postgres` (выбор при старте) |
| `DB_DSN` | `warehouse.db` | Строка подключения (файл SQLite или `postgres://…`) |
| `STATIC_DIR` | `../public` | Каталог статики фронтенда |
| `PRIVATE_DIR` | `../private` | Каталог страницы кладовщика |
| `BACKUP_DIR` | `backups` | Каталог резервных копий |
| `SMSRU_API_KEY` | — | Ключ sms.ru (можно задать в кабинете) |
| `PG_HOST/PG_PORT/PG_DB/PG_USER/PG_PASSWORD` | — | Фолбэки для миграции в PostgreSQL |

> В Go/Rust бэкенд выбирается при старте через `DB_BACKEND`; миграция и
> переключение на лету тоже поддерживаются (из кабинета), но после рестарта
> берётся `DB_BACKEND`.

### Настройки в кабинете

Вкладка **«Настройки»** (только для администраторов):

- **О программе** — версия, время сервера, аптайм, нагрузка, число запросов к
  БД/Redis за час; кнопки «Проверить обновления» и «Обновить».
- **Аналитика** — графики посещений и броней, разбивка по устройствам.
- **Redis** — хост/порт/пароль/БД, включение кэша, кнопка «Тест».
- **PostgreSQL** — параметры подключения, миграция и переключение СУБД.
- **TTL кэша** — время жизни кэша по категориям (слоты, справочники и т.д.).
- **Резервное копирование** — скачать/восстановить, автобэкап (интервал и число
  хранимых копий), список копий.
- **Интеграция с 1С** — токен API, адрес сервера 1С, имя пользователя и пароль,
  адреса проверки заказа и оплаты, тумблеры «разрешить бронь без счёта /
  с недостоверным счётом / предупреждать».
  Пароли и ключи (1С, PostgreSQL, Redis, sms.ru) в кабинет **не возвращаются**:
  в поле выводится подсказка «задано» или «не задано». Пустое поле при
  сохранении означает «не менять», прочерк `-` — очистить значение.
- **Права доступа по разделам** — таблица «роль × раздел» с уровнями
  «нет доступа», «только чтение», «чтение и запись». По умолчанию всё
  разрешено. Администратору доступно всё, независимо от таблицы. Разделы
  «Водители» и «Журнал» помечены как содержащие персональные данные.
- **Обязательные поля записи** — включение/выключение обязательности полей
  «Класс машины» и «Вид загрузки» на странице записи, в записи в три шага
  и во внешнем API.
- **Часовой пояс склада** — общее смещение от UTC (Москва = 3). У каждого склада
  можно задать собственный пояс в карточке склада; пустое поле — берётся общий.
  Пояс определяет правило «записаться минимум за N минут», статус «Просрочено»,
  максимальную дату и время, показываемое клиенту и в кабинете.
- **За сколько минут до начала окна можно записаться** — по умолчанию 45,
  0 — без ограничения.
- **За сколько дней можно записаться** — горизонт записи (1–365, по умолчанию 14).
- **Сообщение на странице записи** — текст-баннер вверху страницы записи (пусто —
  скрыт).
- **Политики** — текст политики обработки ПДн и политики cookie.
- **Логотипы** — свои логотипы под темы.
- **Прочее** — журналирование действий, работа по выходным, включение маскота,
  разрешённые подсети (IP-allowlist для кабинета/кладовщика), баны телефонов/IP.

### HTTPS / домен

- **Docker**: nginx + certbot уже в `docker-compose.yml`; сертификат —
  `deploy/init-letsencrypt.sh`.
- **Native (Go/Rust/Node)**: запустите установщик с `WITH_NGINX=1 DOMAIN=…`,
  затем `apt install certbot python3-certbot-nginx && certbot --nginx -d ВАШ_ДОМЕН`.
- За прокси для Node задайте `TRUST_PROXY=1`, чтобы корректно определялись IP.

## Использование

### Страница записи

Адрес: `/`. Вверху может выводиться информационный баннер (настройка
«Сообщение на странице записи»). Шаги для клиента:

1. Выбрать склад (если их несколько) и тип отгрузки (мелкая/крупная).
2. Выбрать класс машины и вид загрузки (справочники из кабинета).
3. Выбрать дату (будни; выходные — если включены в настройках) — отобразится
   сетка свободных слотов. Свободны слоты не раньше чем через час и не дальше
   горизонта записи (настройка «За сколько дней можно записаться»).
4. Выбрать слот, заполнить имя, телефон, при необходимости номер счёта,
   организацию, комментарий. Поля «Класс машины» и «Вид загрузки» обязательны,
   если это включено в настройках.
5. Поставить галку согласия на обработку ПДн, решить капчу, подтвердить.

**Время.** Окна показываются по времени склада (по умолчанию московскому).
У каждого склада в его карточке указан пояс, а под названием и адресом склада
выводится строка «Работает по московскому времени» либо «Работает по местному
времени (UTC+5)». Если часовой пояс браузера отличается от пояса склада, под
каждым интервалом дополнительно показывается местное время клиента, а в окнах
подтверждения — в скобках.

**Категории товаров.** Если складу назначены категории, внизу его плашки есть
ссылка «Категории товаров (N)» — по нажатию раскрывается список того, что
хранится на складе. Раскрытие не меняет выбранный склад; работает и с
клавиатуры. У склада без категорий ссылки нет.

**Организация.** Если указан номер счёта и настроена проверка в 1С, организация
берётся из ответа 1С: введённое клиентом название заменяется на достоверное.
Когда счета относятся к разным юрлицам, в заявке перечисляются все.

После брони клиенту уходит SMS (если задан ключ sms.ru). Свободные слоты
кэшируются в Redis (если включён) и обновляются при бронях и отменах. Окно
записи адаптировано под мобильные (полноэкранная форма, крупные поля, кнопки
закреплены внизу).

### Кабинет менеджера

Адрес: `/manager.html`. Вход — логин/пароль менеджера. В шапке — **текущее время
сервера** (в часовом поясе склада) и ссылка **«Кабинет кладовщиков»**. Вкладки
переносятся по ширине экрана.

- **Заказы** — фильтр по дате/типу/складу; по каждой брони действия: подтвердить,
  передать кладовщику, взять на сборку, **завершить** (доступно на любом этапе),
  отменить, вернуть со сборки. Виден клиент, телефон, счёт, организация,
  комментарий, менеджер/инженер из 1С. Если счета относятся к разным юрлицам,
  в колонке «Счёт» они сгруппированы по организациям — над каждой группой
  выводится название, а в колонке «Организация» юрлица перечислены по строкам.
  Колонки «Заявка», «Подтв.», «У кладовщ.», «На сборке», «Заверш.» показывают
  время по часовому поясу склада (в базе отметки хранятся в UTC). Рядом с менеджером/инженером — кнопки
  **✉ отправить SMS** (номер берётся из имени, текст предзаполняется шаблоном).
- **Статистика** — общая статистика по заказам за период.
- **Статистика сотрудников склада** — по кладовщикам, плюс блоки **«Статистика
  менеджеров»** (время от подачи до передачи кладовщику) и **«Статистика по
  обработке заказов»** (время от подачи до готовности).
- **Кладовщики** — список с PIN-кодами (PIN не отображается, только признак «задан»).
- **Склады** — список складов: название, адрес, **категории товаров**, часовой
  пояс, признак «по умолчанию». В карточке склада задаются адрес, часовой пояс,
  описание и схема проезда, маршрут из Москвы и набор категорий товаров —
  отметьте, что хранится на этом складе. Новую категорию можно завести прямо
  из карточки, она попадёт в общий справочник. Переименование категории
  автоматически отражается на всех складах, удаление — снимает её со складов.
- **Справочники** — классы машин, виды загрузки, категории, контрагенты.
- **Менеджеры** — создание/редактирование, признак «администратор» (главного
  `admin` нельзя разжаловать или удалить).
- **1С / данные** — заказы 1С, журнал проверок, сообщения, номенклатура, водители.
- **Настройки** — см. раздел [Настройки в кабинете](#настройки-в-кабинете).

### Страница кладовщика

Адрес: `/storekeeper`. Кладовщик вводит **PIN-код** (заданный менеджером) и
видит активные и завершённые отгрузки; может отметить «на сборку» и «завершено».
Доступ к странице дополнительно ограничивается списком разрешённых подсетей
(если он задан в настройках).

### Интеграция с 1С

1. В кабинете → «Настройки» → «Интеграция с 1С»: сгенерируйте **токен API**,
   укажите адрес сервера 1С, имя пользователя и **пароль** (видимое поле,
   кнопка «Сохранить»).
2. Укажите **адрес проверки заказа** и **адрес проверки оплаты/готовности**.
   Под каждым полем показывается пример запроса (метод, URL, заголовок
   `Authorization: Basic <base64(логин:пароль)>`, тело `{ "invoce_number": [...] }`).
3. Кнопкой «Тестировать запрос» проверьте связь, указав номера счетов.
4. Тумблеры определяют, можно ли бронировать без счёта или с недостоверным
   счётом и нужно ли предупреждать.

При бронировании, если задан адрес проверки заказа, бэкенд обращается к 1С,
пишет результат в журнал проверок и блокирует бронь при недостоверном счёте
(если это не разрешено тумблером).

## Обслуживание

**Управление сервисом (native, systemd):**

```bash
systemctl status warehouse-go     # или warehouse-rs / warehouse (Node)
systemctl restart warehouse-go
journalctl -u warehouse-go -f      # логи в реальном времени
```

**Docker:**

```bash
docker compose ps
docker compose logs -f app
docker compose pull && docker compose up -d   # обновление образа
```

**Резервные копии.** Скачивайте дамп из кабинета или настройте автобэкап
(интервал + число хранимых копий). Файлы — в `BACKUP_DIR`. Восстановление — из
кабинета (загрузка дампа) или выбором автокопии.

> Дамп содержит **секреты** (токен 1С, пароли PostgreSQL/Redis) и персональные
> данные клиентов — храните копии в защищённом месте, вне каталога, который
> раздаёт веб-сервер.

**Обновление.** `./update.sh` в каталоге приложения: делает резервную копию кода
и файлов SQLite, забирает изменения из git (или из папки через `--source`),
переустанавливает зависимости при изменении `package-lock.json`, перезапускает
приложение и проверяет, что оно отвечает. Откат — `./update.sh --rollback`.

> Если приложение запускается без systemd, `update.sh` останавливает **все**
> процессы `node server.js` и поднимает один. Проверить, что процесс один:
> `pgrep -fa 'node .*server.js'`. Два процесса — самая частая причина того, что
> после обновления кабинет продолжает работать на старом коде. Убедиться, что
> код новый, можно так:
> `curl -s http://127.0.0.1:3000/api/public/settings/required-fields` — должен
> вернуться JSON, а не «Cannot GET».

**Миграция SQLite↔PostgreSQL.** В кабинете → «Настройки» → PostgreSQL: задайте
параметры и нажмите «Мигрировать» (копирует данные и переключает) или
«Переключить» (без копирования). Для Go/Rust после рестарта используется
`DB_BACKEND`, поэтому зафиксируйте выбор в переменных окружения сервиса. После
ручной миграции в PostgreSQL при необходимости выполните
`deploy/fix-pg-sequences.sql` для пересинхронизации счётчиков id.

**Обновление.** Native: кнопка «Обновить» в кабинете (git pull + рестарт) либо
`deploy/auto-deploy*.sh`. Docker: pull нового образа или Watchtower.

## Безопасность

- Пароль главного администратора генерируется при создании пустой базы и
  записывается в файл `ADMIN-PASSWORD.txt` (права 0600). Войдите, смените
  пароль и удалите файл. Задать свой пароль заранее можно переменной
  `ADMIN_PASSWORD`.
- Пароли менеджеров хранятся в виде scrypt-хеша с солью. Старые хеши прежнего
  формата продолжают работать и заменяются на новые при первом входе.
  Минимальная длина пароля — 8 символов, пароль не должен содержать логин.
- **Защита от подбора пароля**: после 5 неудачных попыток пара «IP + логин»
  блокируется с нарастающей паузой (от 30 секунд до 15 минут), каждая неудача
  попадает в журнал действий.
- Секрет подписи сессий хранится в файле `.session-secret` (создаётся
  автоматически) либо задаётся переменной `SESSION_SECRET`. Файл не должен
  попадать в репозиторий — он в `.gitignore`.
- При работе по HTTPS задайте `COOKIE_SECURE=1`, чтобы cookie сессии не
  передавалась по открытому каналу.
- **Права доступа по разделам** ограничивают, что видит и меняет рядовой
  менеджер и кладовщик (Настройки → «Права доступа по разделам»).
- Ограничьте доступ к кабинету и кладовщику по IP (настройка «Разрешённые
  подсети»). На loopback и при пустом списке доступ открыт.
- PIN-коды кладовщиков и пароли менеджеров не отдаются клиенту. Пароли внешних
  систем (1С, PostgreSQL, Redis, sms.ru) в кабинет тоже не возвращаются —
  показывается только признак «задано».
- Резервные копии содержат персональные данные и хеши паролей — храните их вне
  каталога, который раздаёт веб-сервер, и защищайте доступ.
- Приложение выставляет заголовки `X-Frame-Options`, `X-Content-Type-Options`,
  `Referrer-Policy`; кросс-доменные запросы к кабинету запрещены, если сайт не
  указан в `CORS_ORIGINS`.
- Включайте HTTPS (см. [HTTPS / домен](#https--домен)). **Обязательно** задайте
  `TRUST_PROXY=1`, если приложение за nginx/прокси — иначе IP-фильтр и
  автоблокировки будут видеть адрес прокси (127.0.0.1), а не клиента. Без прокси
  переменную не ставьте (иначе клиент сможет подделать `X-Forwarded-For`).
  Скрипты `install-*-server.sh` при `WITH_NGINX=1` выставляют `TRUST_PROXY=1`
  автоматически.
- Капча и лимит частоты броней снижают автоматизированный спам.

**Автоблокировки IP** (во всех вариантах). IP заносится в чёрный список на сутки,
если он **не входит** в разрешённые сети и:

- сделал **более 3 заявок за сутки**, либо
- **более 5 раз подряд** неверно ввёл капчу.

Авто-баны имеют пометку «Автобан» в кабинете (вкладка «Забаненные IP»), истекают
через 24 часа и снимаются автоматически; ручные баны — бессрочные. И то, и другое
можно снять вручную.

## Устранение неполадок

- **Слоты не отображаются** — проверьте, что выбран будний день (или включена
  работа по выходным), и что склад создан. Слоты создаются «лениво» при запросе.
- **PostgreSQL: `column … does not exist` / `duplicate key`** — после миграции
  выполните `deploy/fix-pg-sequences.sql`; убедитесь, что схема создана.
- **Redis не кэширует** — включите Redis в «Настройках» и нажмите «Тест»; кэш
  работает только при `redis_enabled=1` и доступном сервере.
- **Изменения в справочниках «не применяются» (категория, склад, кладовщик не
  появляются в списке)** — так выглядел дефект инвалидации кэша: ключи
  справочников хранятся без двоеточия (`categories`, `warehouses`,
  `storekeepers`), а сброс удалял только `префикс:*`, поэтому список ещё до 5
  минут отдавался старым. Исправлено: `redisFlushByPrefix` удаляет и сам ключ.
  Если симптом вернулся — проверьте, что после изменения данных вызывается
  сброс нужного префикса, и прогоните `test/cache.test.js` с `E2E_REDIS=1`.
- **Категории склада не видны на странице записи** — склад сохраняется с тем
  набором категорий, который отмечен галками в его карточке; после добавления
  новой категории кнопкой «+ Категория» её нужно оставить отмеченной и нажать
  «Сохранить». Публичный список `/api/warehouses` отдаёт категории названиями и
  не кэшируется, поэтому изменения видны сразу после перезагрузки страницы.
- **SMS не приходят** — задайте ключ sms.ru (кабинет или `SMSRU_API_KEY`).
- **Доступ к кабинету «Access denied from this IP»** — ваш IP не в списке
  разрешённых подсетей; добавьте подсеть или очистите список.
- **Go/Rust не собираются** — выполните `go build ./...` / `cargo build` и
  пришлите вывод; для Rust нужен C-компилятор (`build-essential`).
- **Порт занят** — измените `PORT`.

## Ограничения и заметки

- Go и Rust выбирают СУБД при старте через `DB_BACKEND`; переключение на лету
  доступно, но не сохраняется между перезапусками.
- Контракт проверки 1С: `POST` с HTTP Basic-аутентификацией (логин/пароль 1С) и
  телом `{ "invoce_number": ["<счёт>"] }` (поле названо именно так, с опечаткой —
  как в API 1С). Ответ разбирается по объекту `results`: счёт считается валидным,
  если его `status` начинается с `found`/`найден`. Если поля `results` нет или
  ответ не разобрать — проверка пропускается (бронь не блокируется). Одинаково
  во всех трёх вариантах.
- Сервер Rust однопоточный (один цикл обработки) — этого достаточно для
  внутреннего складского приложения; внешние вызовы (1С/SMS) имеют таймауты.
- Дефолтные учётные данные `admin`/`admin123` обязательно меняйте.
- **Менеджеру можно назначить несколько складов** (мультивыбор в форме менеджера).
  Обычный менеджер видит заказы только назначенных складов, администратор — все;
  без назначения — все. В «Заказах» есть мультифильтр по складам.

### Различия реализаций

**Node.js — эталонная и наиболее полная** реализация. Варианты **Go** и **Rust** —
«ядро паритета»: основной поток (запись, кабинет, слоты, действия, справочники,
1С-проверка, SMS, Redis-кэш, миграция БД, автоблокировки, мультисклады) есть во
всех трёх. Часть **второстепенных эндпоинтов реализована только в Node** и в
Go/Rust соответствующие вкладки/кнопки не работают:

- `GET /api/manager/stats/storekeepers` — блок статистики кладовщиков;
- `POST /api/manager/verify-pin` — проверка PIN;
- `GET/POST /api/manager/settings/autobackup` — настройки автобэкапа (в Go/Rust
  автобэкап работает по внутреннему значению, но UI-настройка его не меняет);
- `POST /api/manager/settings/logo/reset` — сброс логотипа;
- CRUD складов `POST/PUT/DELETE /api/manager/warehouses[/:id]`;
- в Rust дополнительно нет `GET /api/manager/orders-1c` и
  `…/orders-1c/by-account/:acc/items`.

Если планируете эксплуатировать Go/Rust как основной сервер — эти эндпоинты стоит
доперенести (могу сделать по запросу).

## Разработка и тесты

- Связь «склад ↔ категория» хранится в таблице `warehouse_categories`
  (`warehouse_id`, `category_id`, уникальная пара). Внешних ключей с каскадом в
  схеме нет, поэтому связи чистятся в обработчиках удаления склада и категории.
- **`schema.sql`** — канонический источник схемы БД. При изменении структуры
  правьте его первым, затем три реализации (`database.js`, `go-service/db.go`,
  `rust-service/src/db.rs`) и добавляйте ALTER-миграцию для существующих БД.
- **Юнит-тесты (Node):** `npm test` — на `node:test` (без внешних зависимостей),
  покрывают чистые функции из `lib/util.js` (IP/CIDR, нормализация складов).
  CI: `.github/workflows/node-test.yml`; сборка Go/Rust — `go-build.yml` /
  `rust-build.yml`.
- **Тесты приложения** — каталог `test/`, запускаются напрямую через `node`:

  | Файл | Что проверяет | Нужен запущенный сервер |
  |------|---------------|-------------------------|
  | `passwords.test.js` | Хеширование паролей, совместимость со старыми хешами | нет |
